# Sillypoint Backend

Cricket tournament management backend/API: tournaments, teams, fixture generation, ball-by-ball scoring, live scores, stats. Users: organizers, team managers, scorers, public spectators (no login).

## Stack
Express 5, TypeScript (ESM, NodeNext), Drizzle ORM + `postgres`, PostgreSQL. Env: `DATABASE_URL` (see `.env.example`).
Installed standards: `zod` (validation), `argon2` (hashing OTPs), `jsonwebtoken` (JWT), `multer` (multipart uploads, memory storage), `cloudinary` (image storage), `sanitize-html` (user HTML).
Undecided (ask before adding): WebSocket library, test runner, logger. No Redis for MVP.

## Commands
- `npm run dev` — tsx watch
- `npm run build` — `tsc` (use to type-check)
- `npm run db:generate` / `npm run db:migrate` — Drizzle Kit (see `db-migration` skill)
- `npm run check:scoring` — runs `scripts/scoring-scenarios.ts` (worked cricket scenarios against the pure scoring engine; plain `node:assert`, not a test runner)

## Layout
Feature modules + pure engines (adopt as each feature starts; don't scaffold empty folders):
- `src/modules/<feature>/` — `*.routes.ts` → `*.controller.ts` → `*.service.ts` → `*.repository.ts` (+ `*.schema.ts` zod, `*.constants.ts`). Features: auth, tournaments, teams, fixtures, matches, scoring, stats, announcements, public.
- `src/engines/` — pure TS (fixtures, scoring, standings, stats). No imports from express, db or modules.
- `src/realtime/` — WebSocket server and match hub.
- `src/shared/` — `http/response.ts` (`success`, `failure`), middleware (authenticate, authorize, validate, error-handler), utils (shuffle), `constants/` (constants used by more than one module).
- `src/db/` — `schema/*` re-exported from `schema/index.ts`. `src/routes.ts` mounts module routers under `/api`.
Dependency direction: routes → controller → service → repository → db; service → engines. See `add-endpoint` skill.
(Current code still uses `src/routes` + `src/handlers` + `src/helpers`; migrate when Sprint 1 starts.)

## Conventions
- Relative imports end in `.js`; use `import { type X }` for types.
- 4-space indent, double quotes, no semicolons.
- `strict` + `noUncheckedIndexedAccess` are on; no `any`.
- Constants (magic numbers, TTLs, fixed messages, limits) never live in service/controller/repository/routes files. Put them in `src/modules/<feature>/<feature>.constants.ts` (UPPER_SNAKE_CASE, exported); if used by 2+ modules, put them in `src/shared/constants/`. Import them with the `.js` suffix.
- Tables: identity integer `id`, snake_case columns, `timestamp(..., { withTimezone: true })`.

## Auth
Mobile + OTP only: no passwords or PINs. Signup and login are the same flow: `POST /api/auth/request-otp` (new mobile -> `signup` OTP, verified user -> `login` OTP; same response `{ userId, purpose }` either way) -> `verify-otp` (a correct OTP means the user is logged in; `signup` also activates the user), with optional `resend-otp`. `otp` table purposes: `signup` / `login`. Hash OTPs; never log secrets (the OTP is only console-logged until MSG91 is added).
OTP limits (constants in `auth.constants.ts`): 4 digits, 10-min expiry, 5 wrong guesses, 5 resends, then a 30-min block; the OTP row is locked (`FOR UPDATE`) while verifying/resending.
Sessions: `verify-otp` returns a 15-min access JWT in the body (frontend keeps it in memory, sends `Authorization: Bearer`) and sets a 7-day refresh JWT as an HttpOnly, SameSite=Strict cookie (`Path=/api/auth`, `Secure` in production). Access and refresh tokens use different secrets (`ACCESS_TOKEN_SECRET`, `REFRESH_TOKEN_SECRET`, each 32+ chars, must differ; also `CLIENT_ORIGIN` for CORS). Refresh tokens rotate on every `POST /api/auth/refresh`, only their SHA-256 hash is stored (`refresh_tokens`), reuse of a rotated token ends the whole session family, and a session ends 30 days after login. `POST /api/auth/logout` revokes it. Protect routes with `authenticate` (`src/shared/middleware/authenticate.ts`, sets `res.locals.userId`); cookie endpoints also use `requireAllowedOrigin`. JWT helpers: `src/shared/utils/jwt.ts` (HS256 pinned, issuer + audience checked); env is validated in `src/shared/config/env.ts`. Frontend: `withCredentials` on `/api/auth/*`, never store the access token in localStorage, serialize refresh calls.

## Tournaments
`/api/tournaments` (`src/modules/tournaments/`): `POST /` (authenticated; multipart `name, description, location, startDate, endDate, lastRegistrationDate, registrationFee, prizeMoney, playersPerSide, substitutesPerSide, logo?`; `playersPerSide` is 5-11 and `substitutesPerSide` is 0-4, both required whole numbers, stored as `players_per_side` / `substitutes_per_side` (defaults 11 / 4 for older rows), returned in every tournament response and, like the registration fee, never changeable after creation (PATCH only accepts `prizeMoney`)), `lastRegistrationDate` (`last_registration_date`, required, not in the past, on or before `startDate`, enforced by `tournaments_registration_deadline_order`) is the last day teams can be added, fixed at creation; every tournament response carries it plus a derived `registrationClosed` (`lastRegistrationDate < today` in `Asia/Kolkata`), adding teams after it is a 409 `REGISTRATION_CLOSED`, and a reschedule may not move `startDate` before it (409), `POST /:id/cancel` (organizer only; POST because CORS allows only GET/POST), public `GET /` (filters `q, status, registrationOpen` (only `true`: not cancelled and `lastRegistrationDate >= today`, closing soonest first), `startFrom, startTo, organizerId`, paging `page, limit`) and public `GET /:id` (includes `organizer: { id, mobile }`); `GET /:id/teams` is public too, but with a valid Bearer token from the tournament's organizer (`authenticateOptional`: no header = guest, expired/invalid token = 401 like `authenticate`) each team also carries `manager_mobile`, everyone else gets only `manager_name`. `tournaments.organizer_id` references `users.id` (restrict) and is always the logged-in user, never read from the body; only an active user can organize (`authService.getMe`). Only `cancelled_at` is stored; `status` (`upcoming | live | completed | cancelled`) is derived from the dates in `Asia/Kolkata` (`TOURNAMENT_TIMEZONE`). The description is HTML from the rich text editor and is sanitized to `DESCRIPTION_ALLOWED_TAGS` before saving. Logos go through `imageUpload` (`shared/middleware/upload.ts`, 2 MB, png/jpeg/webp) to Cloudinary (`shared/storage/cloudinary.ts`); `CLOUDINARY_CLOUD_NAME`, `CLOUDINARY_API_KEY` and `CLOUDINARY_API_SECRET` are read lazily, so the server starts without them and only logo uploads fail. `validate(schema, "params" | "query")` puts parsed values in `res.locals.params` / `res.locals.query`.

## Matches
`src/modules/matches/`, mounted under `/api/tournaments`: `POST /:id/matches` (organizer only, checked in the service; body `teamAId, teamBId, matchDate (YYYY-MM-DD), matchTime (HH:mm), stage?, notes?`; `stage` is one of `MATCH_STAGES` (group_stage, eliminator, qualifier, quarter_final, semi_final, final) or null, and older matches have null) and public `GET /:id/matches` (earliest first, each with `teamA`/`teamB` `{ id, name, logo }`). Date and time are read as `Asia/Kolkata` (`MATCH_TIMEZONE_OFFSET`) and stored as `matches.scheduled_at`. Rules: tournament not cancelled/completed, date within the tournament dates, not in the past, two different teams both enrolled (`areTeamsEnrolled` in the tournaments service). Also `GET /api/matches/:id` (public details; adds `tournament { id, name, logo, location, startDate, endDate, status, organizerId }`) and `PATCH /api/matches/:id/reschedule` (organizer only, body `matchDate, matchTime`; 409 once the match has started (scoring started or the time has passed), has a published result (`completed_at`), or the tournament is cancelled/completed; the update itself only matches rows with no `completed_at` / `scoring_started_at`, so a conclusion racing the request cannot be overwritten). There is no add-scorer step and no scorer name or mobile: every match gets its scorer login when it is created (`createMatch` stores `matches.scorer_link_token` and `scorer_pin`; the `scorer_mobile` and `scorer_name` columns were dropped in migrations 0022 / 0023 and `matches_scorer_valid` only requires the two to be set together). The scorer is not a user account and match responses carry no scorer data.
Scorer login: `matches.scorer_link_token` (32 random bytes, base64url, unique) and a 6-digit `scorer_pin` (stored as plain text on purpose so the organizer can always view it) are generated by `createMatch`. `GET /api/matches/:id/scorer/access` (organizer only) returns `{ linkToken, pin }` (a match created before links existed gets them on the first call). The frontend builds the shareable link `<origin>/scorer/<linkToken>`. Public `POST /api/scorer/login` (body `token, pin`, a mobile is ignored; mounted via `scorerRouter` in `matches.routes.ts`) returns `{ accessToken, match, serverTime, scoringOpensAt }`; an unknown token or a wrong PIN gives the same 401 `Invalid PIN`, 5 wrong tries lock that match's scorer login for 30 minutes (`scorer_pin_attempts`, `scorer_locked_until`; 429), 409 if the tournament is cancelled/completed. The scorer token is a 12-hour JWT signed with the access secret but audience `scorer` (`signScorerToken`), so `authenticate` rejects it as a user token. It is the only scorer credential (no refresh token); the frontend persists it in `localStorage` so a refresh keeps the scorer logged in. `GET /api/scorer/me` (behind `authenticateScorer`, `src/shared/middleware/authenticate-scorer.ts`, which uses `verifyScorerToken` and sets `res.locals.matchId`) returns the same `{ match, serverTime, scoringOpensAt }` read fresh (401 bad/expired token, 409 tournament cancelled/completed). Scoring opens `SCORING_OPENS_BEFORE_MS` (30 min) before `scheduled_at`: `scoringOpensAt` is that moment and `serverTime` lets the client ignore its own clock. Every scoring endpoint must use `authenticateScorer` and then call `assertScoringOpen(matchId)`: it throws 409 if the tournament is cancelled/completed, 403 before the window, and returns the match.
Toss: `matches.toss_winner_team_id` (FK teams) and `toss_decision` (`bat` | `bowl`) are both null or both set (`matches_toss_valid`, which also requires the winner to be team A or B). `PUT /api/scorer/toss` (scorer token, window open; body `winnerTeamId`, `decision`) records or changes it (400 if the team is not in the match) and returns `{ message, match }`. Both fields are part of every match response (public `GET /api/matches/:id`, `GET /api/scorer/me`).
Overs: `matches.overs_per_side` (nullable integer, `matches_overs_valid` keeps it 1-50, `MIN_OVERS_PER_SIDE` / `MAX_OVERS_PER_SIDE`). `PUT /api/scorer/overs` (scorer token, window open; body `oversPerSide`, a whole number 1-50, else 400) records or changes it and returns `{ message, match }`; `oversPerSide` is part of every match response (null until set).

## Squads (match players)
`src/modules/squads/`, mounted at `/api/scorer` (second router next to `scorerRouter`). Players belong to a match, not a team (a team has no roster; the scorer only holds a match token). Table `match_players` (`match_id`, `team_id`, `squad` `playing` | `substitute`, `position`, `name` up to 60); players are names only for now (a role column was added and dropped again in migration 0018). `position` is 1-11 for playing (the batting order) and 1-4 for substitutes, unique per `(match_id, team_id, squad, position)`; checks on name, squad and position. The absolute maximums are in `shared/constants/squads.ts` (`PLAYING_XI_SIZE` 11, `SUBSTITUTES_SIZE` 4); the real limit per match is set by its tournament (`tournaments.players_per_side` / `substitutes_per_side`, see Tournaments).
`GET /api/scorer/players` returns `{ teamA: { team: { id, name, logo }, playing: [{ name }], substitutes: [...] }, teamB: {...} }`. `PUT /api/scorer/players` (body `{ teamA: { playing, substitutes }, teamB: {...} }`, each entry `{ name }`, array order = position; unknown keys such as a leftover `role` are ignored) replaces both teams' players in one transaction (match row locked `FOR UPDATE`); returns the same shape plus `message`. Fewer than the tournament's limit is allowed (the scorer fills the rest in later); more than the tournament allows (checked in `saveSquads` against `match.tournament.playersPerSide` / `substitutesPerSide`, 400 "This tournament allows at most N players/substitutes per team"; the zod schema keeps the absolute 11 / 4 cap), a blank or over-long name, or the same name twice within a team (case-insensitive) is a 400. Both endpoints need the scorer token and `assertScoringOpen`.

## Team history
`GET /api/teams/:id/matches?status=&page=&limit=` (`src/modules/teams/`, logged in; only the team's manager, anyone else's team is a 404 like `GET /api/teams/:id`; unauthenticated 401, bad `status` / `page` / `limit` 400) returns `{ summary: { played, won, lost, tied, upcoming }, matches, page, limit, total }`. `summary` counts all of the team's matches whatever the page or filter. Each match: `id, scheduledAt, stage, state, result, resultSummary, tournament { id, name }, teamA / teamB { id, name, logo, score }`. `state` is decided in this order: `completed` (`matches.completed_at`), `cancelled` (its tournament is cancelled), `live` (`scoring_started_at` set), else `upcoming`; the optional `status` filter uses the same conditions. `result` is relative to the requested team (`won | lost | tied`, null otherwise) and `resultSummary` is the stored text. `score` is `{ runs, wickets, overs }` from that side's `innings` row (left join on `batting_team_id`), null if it has not batted. Newest first (`scheduled_at desc, id desc`), default page size 10, max 50. The queries live in the teams repository (not the matches module) because matches.service imports tournaments.service, which uses teams.service: calling back would create an import cycle.

## Scoring
Ball-by-ball scoring: `src/modules/scoring/` (routes → controller → service → repository) on top of the pure engine `src/engines/scoring/` (no express/db imports; rule messages in `messages.ts`, shared constants in `shared/constants/scoring.ts`). Tables (migration 0021): `innings` (one per side; cached snapshot `runs, wickets, legal_balls, striker_id, non_striker_id, bowler_id`, `version`, `target`, `status` `in_progress|completed`, `end_reason`) and `deliveries` (the immutable event log: one row per ball or per retirement, `seq` unique per innings, the crease **before** the ball stamped by the server, `runs_off_bat` (overthrow runs included), `wides/no_balls/byes/leg_byes` (each including the penalty run), `overthrow_runs`, `is_boundary`, `runs_run` (server-computed, decides the strike change), `is_free_hit`, `wicket_type`, `dismissed_player_id`, `fielder_id`, `voided_at`). Players are `match_players.id`. `matches` gained `scoring_started_at`, `completed_at`, `result_type` (`win|tie|no_result`), `winner_team_id`, `result_summary`. Undo only sets `voided_at` (audit trail); the score and scorecard are derived from the non-voided deliveries.
Rules (engine): total per ball = bat + wides + no_balls + byes + leg_byes; the bowler is charged bat + wides + no_balls (not byes / leg byes); balls faced = legal balls + no-balls; the strike changes when `runs_run` is odd, a dismissed batter leaves an empty place, and at the end of an over (6th legal ball) the batters change ends again whatever the runs were (even runs on the last ball = one change, odd runs = the same batter stays) and the bowler must be chosen again; an overthrow that reaches the rope (4) is not run, so only the runs before the throw rotate the strike; a free hit follows a no-ball (only run out / obstructing the field); bowler quota `ceil(oversPerSide / 5)` overs and no two overs in a row (relaxed only if nobody else is left); the innings ends on all out (`playersPerSide - 1` wickets), overs complete, target reached or the scorer ending it; the second innings decides the match (`computeResult`).
Endpoints (all need the scorer token and `assertScoringOpen`; mutations take `expectedVersion`; a stale or repeated tap is a 409, a broken cricket rule a 400; every response is the fresh full state): `GET /api/scorer/scoring` (`{ match, players, innings[], current, nextInnings }`; `current` = the latest innings with `striker / nonStriker / bowler` lines, `thisOver`, `pending` (`batter` after a wicket, `bowler` after an over), `isFreeHit`, `canUndo`, `canChangeBowler`, `availableBatters / availableBowlers`, chase numbers), `POST /api/scorer/innings/start` (`strikerId, nonStrikerId, bowlerId`; innings 1 batting side comes from the toss, innings 2 starts once the first is over; needs toss + overs + full playing XIs), `POST /api/scorer/innings/:n/deliveries` (`expectedVersion, runs` (everything counted for the ball, penalty run excluded, overthrow runs included), `isBoundary`, `overthrowRuns`, `extra?: { type: wide|no_ball|bye|leg_bye, runKind?: bat|bye|leg_bye (no-ball only) }`, `wicket?: { type, dismissedPlayerId?, fielderId? }`), `/batter`, `/bowler` (also changes the bowler until the first ball of the over), `/swap-strike`, `/retire` (`playerId, type: retired_hurt|retired_out`), `/undo` (not allowed on innings 1 once innings 2 has started, nor once the match is over) and `/end`. The match is concluded automatically: the moment the second innings decides it (the last ball, all out, target reached or the scorer's `/end` on innings 2) the result is saved with `completed_at`, and from then on the match is final. Every later innings change (ball, batter, bowler, swap-strike, retire, undo, end) is a 409 `MATCH_OVER` (checked inside the transaction under the match row lock, so a tap that races the deciding ball loses), `current.canUndo` is false, and `startInnings` refuses a completed match. There is no separate conclude endpoint or column; the scorer's `/me` and `/scoring` match payloads carry `completedAt`, `winnerTeamId`, `resultType` and `resultSummary` so the frontend can show "Match completed" and the winner. Public `GET /api/matches/:id/scorecard` returns `{ match, innings[] }` generated by `buildInningsCard` (batting with strike rate and how out, did not bat, extras, bowling with maidens and economy, fall of wickets, over-by-over timeline, chase).
Once the first innings starts (`matches.scoring_started_at`) the toss, overs and players are locked: `PUT /api/scorer/toss`, `/overs` and `/players` return 409 (`SCORING_STARTED_LOCKED`), because deliveries point at the `match_players` rows that `PUT /players` would replace. `GET /api/scorer/players` now also returns each player's `id`. Every change runs in one transaction with the innings row locked `FOR UPDATE`.

## Profile photos
`users.avatar_url` / `avatar_public_id` (nullable). `PUT /api/users/me/avatar` (authenticated, multipart field `avatar`, 2 MB, png/jpeg/webp) uploads to Cloudinary folder `sillypoint/dp` (`AVATAR_FOLDER`, stored as a 512×512 crop), saves it under a row lock, then deletes the previous image (best effort); if saving fails the new upload is deleted. `DELETE /api/users/me/avatar` deletes the image from Cloudinary **first** and only then clears the columns (a Cloudinary failure returns 502 and keeps the photo, so it can be retried). `deleteImage` returns `true/false` (already-missing counts as deleted) instead of throwing. `GET /api/auth/me`, the `verify-otp` `user` and a tournament's `organizer` all include `avatar` (URL or null). CORS `methods` now include `PUT` and `DELETE`. `src/modules/users/` owns this.

## Domain rules (from PRD)
- Keep engines separate: Tournament/Fixture engine (who plays whom) → Match engine → Scoring engine → Live broadcast. No tournament logic in scoring.
- Fixture generation is independent of scheduling (date/time/venue).
- Dynamic Knockout: server-side Fisher-Yates shuffle, odd count → bye, generated rounds are locked (never regenerate existing matches).
- Team removal behaves by state: before fixtures → just remove; fixtures generated, not started → invalidate + regenerate; started → keep completed matches, cancel future ones.
- Test fixture generators with 4, 5, 8, 10, 20, 21 teams.
- Store every delivery as an immutable event; backend derives authoritative match state (frontend is never the source of truth). Corrections keep an audit trail (original, changed, by, at).
- Concurrency: client sends `expected_version`; reject if it differs from `match_version`. Prevent duplicate deliveries.
- Authorization checks: tournament owner, team owner, assigned scorer (only for their match), valid match state.
- Public endpoints (tournament, match, scorecard, standings, live) need no auth.
- API under `/api/...`; WebSocket at `/ws/matches/:matchId` with events `DELIVERY_RECORDED`, `SCORE_UPDATED`, `WICKET`, `OVER_COMPLETED`, `INNINGS_COMPLETED`, `MATCH_COMPLETED`.
